## 2.「發送測試通知」按鈕

- 需求：在設定頁提供明確的本機測試按鈕，以驗證 Windows Toast 是否顯示、點擊後是否回到 v2，以及失敗時的診斷狀態。畫面須清楚標示「測試」，不能偽裝成真實重大訊息。
- 安全界線：不得查詢 live 官方來源、修改重大訊息去重紀錄、發送 Google Calendar 事件或取得 token；隔離測試模式與正式模式的通知行為須分別驗證。
- 進度：通知控制器／可信 IPC／React UI／隔離 Electron E2E 均已有測試；正式版走原生 Windows channel，隔離模式抑制 Toast，不進入 outbox；點擊路由回設定頁，失敗會顯示並記錄診斷事件。專案作者已回報在新安裝版實際看到 Windows Toast，點擊後返回設定頁，記於 `WIN-TEST-TOAST-01`；不能只憑程式回傳「已接受顯示要求」就宣稱使用者看到了通知。

## 3. 重大訊息刪除／重測新公告通知

- 使用者決定：**正式安裝版採可確認、可追溯的軟刪除並允許重測通知**。從本機列表隱藏單筆已保存公告；同一官方公告再次抓到時，重新顯示並對仍啟用的關注公司允許一次新通知。這不是官方公告的刪除，也不是僅限隔離測試。
- 現況與風險：SQLite 位於 Electron `app.getPath('userData')` 下的 `reporter.sqlite3`，**不在安裝目錄**。`material_events` 與更正關聯、notification outbox／delivery、來源檢查及 job run 有關；直接刪資料庫檔或手動刪資料列，可能破壞歷史追溯、外鍵、去重或通知紀錄，不能當成安全驗收步驟。
- 進度：SQLite v5 `deleted_at` 與獨立稽核表、來源重抓後恢復與通知、跨來源別名去重、匯出、可信 IPC、React 確認操作已以失敗測試先行實作。既有通知、原公告 ID 與更正關聯保留；跨來源對帳若只有摘要，恢復原公告仍保留完整內文。隔離測試不依賴正式資料；最新版 1.0.3 installer 已重建並通過 archive／packaged smoke。專案作者已回報在新安裝版軟刪除成功，重新按重大訊息檢查後收到通知，記於 `WIN-MATERIAL-DELETE-01`；不能由此推論官方來源已達完整即時同步。
- 驗收：自動測試須證明普通重跑不重複通知，軟刪後重抓才允許再通知，並確認舊 outbox／delivery 未移除；正式桌面操作須看到確認視窗與單筆移除。不得以正式 userData 或手動 SQL 刪除作為標準測試。

## 4. 重大訊息降級文案

- 現象：即時來源已取得公告，但因已知可能漏筆而回報 `degraded`，設定頁卻顯示「重大訊息部分來源檢查失敗，請查看最新狀態」，容易誤認完全沒有資料。
- 進度：先以失敗 UI 測試重現，再將重大訊息的 `degraded` 文案改為「來源部分降級、資料可能不完整」，提供前往重大訊息與來源狀態的按鈕，並在來源狀態顯示有效來源回傳筆數；失敗來源不顯示 `0 筆`。仍待顯示本次新存／通知筆數與正式安裝版畫面驗收。
