## 2.「發送測試通知」按鈕

- 需求：在設定頁提供明確的本機測試按鈕，以驗證 Windows Toast 是否顯示、點擊後是否回到 v2，以及失敗時的診斷狀態。畫面須清楚標示「測試」，不能偽裝成真實重大訊息。
- 安全界線：不得查詢 live 官方來源、修改重大訊息去重紀錄、發送 Google Calendar 事件或取得 token；隔離測試模式與正式模式的通知行為須分別驗證。
- 驗收：先做失敗的 UI、IPC／通知 adapter、Electron E2E 測試；另在實際 Windows 安裝版驗證 Toast 外觀與點擊路由。避免只憑 outbox `sent` 就宣稱使用者看到了通知。

## 3. 重大訊息刪除／重測新公告通知

- 使用者決定：**正式安裝版也要提供可確認、可追溯的重大訊息刪除功能**，讓使用者能清除某筆已保存公告，再重新檢查並驗證新公告通知；不是只做隔離測試重置。此功能目前尚未實作。
- 現況與風險：SQLite 位於 Electron `app.getPath('userData')` 下的 `reporter.sqlite3`，**不在安裝目錄**。`material_events` 與更正關聯、notification outbox／delivery、來源檢查及 job run 有關；直接刪資料庫檔或手動刪資料列，可能破壞歷史追溯、外鍵、去重或通知紀錄，不能當成安全驗收步驟。
- 待定設計：正式刪除須決定備份、明確確認、關聯資料處理、重新抓取後是否允許重複通知及稽核紀錄；不能默默把重新抓取視為新的官方公告。隔離測試仍應能注入一筆新的 fixture 公告，不依賴重新播放真實公告。
- 驗收：先以測試證明既有公告不會因重跑而重複通知，另證明隔離測試的新公告會入列、送出 Toast 意圖並可點擊導頁；不得以正式 userData 或手動 SQL 刪除作為標準測試。

## 4. 重大訊息降級文案

- 現象：即時來源已取得公告，但因已知可能漏筆而回報 `degraded`，設定頁卻顯示「重大訊息部分來源檢查失敗，請查看最新狀態」，容易誤認完全沒有資料。
- 待做：區分「取得資料但可能不完整」與「來源實際失敗」，並同時顯示本次取得／新存／通知筆數或可前往來源狀態的入口。先以 UI 測試重現誤導文案，再修正。
